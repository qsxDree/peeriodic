System Summary

Peeriodic is a real-time collaborative Markdown editor built with Go and React. It resolves concurrent edits with a centralized Operational Transformation engine. The architecture uses PostgreSQL for persistence and streams live presence over WebSockets.

B

System Architecture

  • Edge Proxy: Nginx 1.27 serves the React SPA and proxies REST traffic to /api/* and WebSocket connections to /ws.
  • Backend Monolith: A single Go binary runs the HTTP stdlib router, middleware pipeline (recovery, rate limiting, logging, CORS, body limits), WebSocket hub, and OT engine.
  • Data Layer: PostgreSQL 16 stores user accounts, room documents, membership grants, invite links, and operation logs.
C

Collaborative Edit Flow

  1. Local Mutation: CodeMirror captures input; ClientOTState diffs changes into atomic insert and delete operations.
  2. Client State Machine: If synchronized, the client dispatches operations immediately. The client queues subsequent edits into a local buffer while awaiting server acknowledgement.
  3. Server Transformation: Under mutex locking, DocumentState validates and transforms operations against the revision history.
  4. Broadcast & Ack: Origin receives an ack with the new revision; other active collaborators receive transformed operations.
  5. Asynchronous Durability: Background goroutines persist operations and periodically snapshot document contents to PostgreSQL.

Concurrency Engine & OT Mechanics

Centralized Operational Transformation
Server Authority
  • Monotonic Revision NumberSingle source of truth per room
  • DocumentState MutexSerializes all concurrent operations
  • History Ring BufferRetains last 1,000 revisions for fast catchup
Rune Offset Mathematics
  • Rune-based slicingPrevents UTF-8 and multibyte character splits
  • Atomic Op TypesRetain, Insert, Delete primitives
Client State Machine
  • SynchronizedLocal doc matches server rev with no edits in flight
  • AwaitingAckOne operation sent to server awaiting confirmation
  • AwaitingWithBufferAdditional keystrokes queued in local buffer
  • Rune-Safe Indexing: The system calculates all operation offsets using Unicode runes ([]rune in Go, Array.from in TypeScript) to avoid splitting multibyte characters.
  • Centralized Revisioning: The server maintains an incremental rev counter per room. When client revisions lag behind, the server transforms incoming operations against missed history records.
  • In-Memory History: Server keeps the last 1,000 revisions in memory for instant incremental catch-up when clients reconnect.

Authorization & Access Control Waterfall

Effective Role Evaluation
1. Room Creator CheckIf user UID matches rooms.user_uid -> OWNER
2. Document Member TableIf row exists in document_members -> ASSIGNED ROLE
3. Public Access FallbackUses rooms.public_role (Default: EDITOR)
  • Role Levels: owner (full document deletion and member management), editor (read and write operations), and viewer (read-only real-time observation).
  • Public Default: Rooms default to public_role = 'editor', enabling instant link-based collaboration without authentication.
  • Invite System: Cryptographic UUID tokens provide role-based invitation links with optional expiration timestamps.

Data Model & Persistence Architecture

PostgreSQL Schema Architecture
  • usersAccounts with bcrypt hashes, UUID identifiers, and timestamps
  • roomsDocument aggregates with markdown snapshots, current_rev, and public_role
  • document_membersExplicit per-document role grants (owner, editor, viewer)
  • room_invitesShareable link tokens with expiration timestamp
  • room_operationsAppend-only operation audit log with unique (room_id, rev)
  • schema_migrationsVersion tracking for embedded SQL migration files
  • Hybrid Persistence: Real-time editing occurs in RAM inside DocumentState. The server flushes document snapshots to PostgreSQL every 10 revisions, every 30 seconds, upon room vacancy, or on graceful server shutdown.
  • Audit Logging: Background workers append operation records to room_operations for historical traceability.
